# FIXES — 2026-07-07 — Production `/payouts` 500/503 (Server Components error)

Handoff doc for the next agent (Sonnet / DeepSeek). Read `AGENTS.md` first — this repo runs **Next.js 16.2.5** with breaking changes vs. your training data; consult `node_modules/next/dist/docs/` before writing code.

## Symptoms (from production browser console)

```
payouts:1  Failed to load resource: the server responded with a status of 500 ()
Error: An error occurred in the Server Components render. The specific message
is omitted in production builds... A digest property is included on this error.
[admin] unhandled error Error: An error occurred in the Server Components render...
payouts:1  Failed to load resource: the server responded with a status of 503 ()
```

- The `[admin] unhandled error` prefix comes from `app/admin/error.tsx`, so the failing route is **`/admin/payouts`** (there is also an organizer-facing `/payouts` — confirm which one from the URL).
- A 500 followed by a **503** on retry strongly suggests the Railway container crashed/restarted or the DB connection pool was exhausted — not just a render bug.
- Deployed on **Railway** (`railway.json` at repo root, build root `ticketpulse`).

## Step 1 — Get the real error (do this before changing code)

The production build hides the message; only the `digest` is shown. The actual stack is in **server logs**:

1. `railway logs` (or Railway dashboard → service → Deploy/Runtime logs) around the time of the 500.
2. Search the logs for the digest value shown in the browser console.
3. Also check Railway metrics: memory/CPU at crash time, and whether the service restarted (explains the 503).

Do NOT guess-fix until you have the logged error. The candidates below are ranked hypotheses.

## Step 2 — Likely causes, ranked

### 1. Database schema drift (migrations not applied to prod)
The payouts feature references columns/tables that may be newer than the prod DB:
- `payouts.notes`, `payouts.proofReference`, `payouts.reviewedBy`, `payouts.processedBy`
- `payout_audit_log` table (`payoutAuditLog` in `db/schema`)
- `notifications` table with `payout_*` types

A missing column in the `getPayouts` select (`app/admin/payouts/actions.ts:62-89`) throws during server render → exactly this digest-only 500.

**Check:** compare `drizzle` migrations vs prod DB. Fix: run `npm run db:migrate` (or `db:push`) against the production `DATABASE_URL`.

### 2. DB connection exhaustion / connectivity
`/admin/payouts` render fires several queries: `getPayouts` (2 queries) + `Promise.all` for organizers and events (`app/admin/payouts/page.tsx:71-85`). If the Postgres driver in `db/index` has no/low pool limits on Railway, concurrent admin loads can exhaust connections → 500s, then 503 while the service restarts.

**Check:** logs for `ECONNREFUSED` / `too many connections` / timeout. Fix: configure pool size / use pooled connection string.

### 3. `getPayouts` throws `"Unauthorized"` during render
`app/admin/payouts/actions.ts:49-53` throws if the session is missing/expired instead of redirecting. An expired session on `/admin/payouts` = unhandled throw in a server component = this exact error.

**Fix:** in `app/admin/payouts/page.tsx`, check `auth()` at the top and `redirect("/auth/signin")` (as `app/payouts/page.tsx:59-63` already does) instead of relying on the action's throw. Same hardening for the organizer `/payouts` actions if applicable.

### 4. Neon pool crashes the process on idle-connection errors ← likely the 503
`db/index.ts:20` creates `new Pool({ connectionString: url, max: 10 })` with **no `error` listener**. `@neondatabase/serverless` `Pool` is an EventEmitter: when an idle connection drops (Neon closes idle WebSockets aggressively), it emits `'error'`, and an unhandled `'error'` event **crashes the Node process**. That produces exactly this pattern: one request 500s, the container dies, the next requests 503 until Railway restarts it.

**Fix:** add after the pool is created in `db/index.ts`:
```ts
pool?.on("error", (err) => {
  console.error("[db] idle pool connection error", err)
})
```
Also consider `idleTimeoutMillis` lower than Neon's idle cutoff so the pool retires connections before Neon kills them.

### 5. Unbounded/bad data in render
`app/admin/payouts/page.tsx:284-285` indexes `STATUS_STYLE[p.status as PayoutStatus]` — a payout row with an unexpected status renders `undefined` (won't 500, but note it). `Number(p.amount)` on null would render `NaN`, also non-fatal. Low priority.

## Step 4 — Additional improvements found in the payouts code (2026-07-07 review)

Not the cause of the outage, but worth fixing while in here. Ordered by impact.

### 4.1 Server actions throw `Error` for validation — users get the generic crash page (HIGH)
Every validation failure in `app/payouts/actions.ts` and `app/admin/payouts/actions.ts` is a thrown `Error` ("Insufficient balance", "Please enter a valid EcoCash number", "Cannot approve payout in ... status", "Unauthorized", …). In production, a thrown error from a server action surfaces as the **digest-only Server Components error** — the user sees the crash boundary, not the message. This is very plausibly what the admin actually experienced when clicking Approve/Reject/Record.

**Fix:** return `{ ok: false, error: string }` from actions instead of throwing for expected failures, and render the message in the form via `useActionState` (client components) or a `?error=` search param. Reserve `throw` for genuinely unexpected states.

### 4.2 Duplicate payout race — pending check isn't actually serialized (HIGH)
`requestPayoutAction` (`app/payouts/actions.ts:292-306`) checks for an existing active payout inside the transaction, but two concurrent transactions at READ COMMITTED can both see "no pending payout" and both insert. Money-adjacent, so close it properly with a partial unique index:

```sql
CREATE UNIQUE INDEX payouts_one_active_per_user
  ON payouts (user_id)
  WHERE status IN ('pending', 'approved', 'processing');
```

Then catch the unique-violation in the action and return the friendly "already have a pending request" message.

### 4.3 `count()` comes back as a string — comparison/pluralization bugs (MEDIUM)
The stats queries use `sql<number>\`count(...)\`` but postgres `count()` returns `bigint`, which the driver hands back as a **string**. `sql<number>` is only a type assertion. Concrete symptom: `stats.pending !== 1` in `app/admin/payouts/page.tsx:131` is always true (`"1" !== 1`), so the pluralization is wrong; any future arithmetic on these will concatenate. **Fix:** append `.mapWith(Number)` to each stat (or cast `::int` in the SQL) in both `getPayouts` and `getOrganizerPayouts`.

### 4.4 Cash payouts stored as `bank_usd` + magic strings (MEDIUM)
`recordManualPayoutAction` (`app/admin/payouts/actions.ts:174-177`) stores cash payouts with `method: "bank_usd"` and `bankName: "Manual cash payment"`, and both payout pages detect them via `isManualCashPayout()` string-matching on `bankName`/`notes`. Any admin who edits the bank name or notes silently reclassifies the payout, and reporting by method is wrong (cash counted as bank). **Fix:** add `"cash"` to the payout method enum (one migration) or add a boolean `recorded_manually` column, then delete `isManualCashPayout()`.

### 4.5 `notes` column doubles as a JSON snapshot store (LOW)
`requestPayoutAction` writes a JSON blob (revenue snapshot) into `payouts.notes`, while `recordManualPayoutAction` writes human prose into the same column, and `isManualCashPayout` greps it. Move the snapshot to a dedicated `jsonb` column (e.g. `balance_snapshot`) so `notes` is reliably human text.

### 4.6 Admin manual-payout form UX (LOW)
In `app/admin/payouts/page.tsx`: the Event dropdown lists the latest 200 events for *all* organizers — selecting a mismatched pair only fails server-side (as a thrown error, see 4.1). Filter events by the selected organiser client-side, or group the `<option>`s per organiser. Also `updatePayoutStatusAction` permits any status→status transition with no guard or organizer notification — either add transition rules like the other actions or remove it if unused.
